## 4. ESM 마이그레이션

### 4.1 배경
- CommonJS (require/module.exports) 사용
- ESM으로의 전환 필요
- 모듈 의존성 추적 어려움

### 4.2 수행 내용

**점진적 하이브리드 전략**:
- package.json에 `"type": "module"` 전역 설정 대신 새 코드만 `.mjs` 확장자로 작성
- 기존 191개 .js 파일은 그대로 유지 (리스크 최소화)

**8개 .mjs ESM 파일 생성**:
- `app/domain/interfaces/IMonitoringRepository.mjs`
- `app/domain/models/Metric.mjs`
- `app/application/monitoring/GetSystemStats.mjs`
- `app/application/monitoring/GetErrorSummary.mjs`
- `app/infrastructure/prisma/MonitoringRepository.mjs`
- `app/infrastructure/di/container.mjs`
- `app/interfaces/http/MonitoringController.mjs`
- `app/interfaces/http/monitoringRouter.mjs`

**app.js 동적 import()**:
```javascript
// ESM 모듈 동적 로드 (CommonJS와의 호환성)
const { createDIContainer, diMiddleware } = await import('./app/infrastructure/di/container.mjs')
  .catch(() => require('./app/infrastructure/di/container'));
```

**Jest 설정**:
- .mjs 변환 규칙 추가했다가 제거 (기존 Prisma mock 설정과 충돌 causing 33 test failures)
- .mjs 파일은 테스트에서 직접 import되지 않으므로 변환 불필요

### 4.3 핵심 결론
- 191개 파일 규모의 프로덕션 코드베이스에서 전역 `"type": "module"` 전환은 높은 위험
- 하이브리드 접근 (새 코드 .mjs, 기존 코드 .js)이 안전한 점진적 마이그레이션 경로
- ESM 전용 기능 (top-level await, tree-shaking)은 새 모듈부터 활용 가능
