## 1. 핵심 판단

현재 가장 큰 문제는 기능 수보다 **실제 실행 경로, 결제 원장 신뢰성, 검증과 배포의 연결**이다. 지정된 시작 파일은 실제 앱을 실행하지 않는다. 이를 고치더라도 CORS와 현금·포인트 결제 흐름이 서비스 정상 동작과 장부 정확성을 저해한다. 따라서 AI 기능 추가나 대규모 구조 개편보다 아래 P0/P1 개선을 먼저 진행해야 한다.

**현 소스를 그대로 배포하는 것은 권고하지 않는다.** 이 판단은 로컬 소스 기준이다. 현재 운영 서버가 같은 커밋을 실행하는지, 실제로 장애가 발생했는지는 원격으로 확인하지 않았다.

P0는 서비스 제공 또는 결제 신뢰성을 직접 막는 항목, P1은 금전·개인정보·배포 통제에 영향을 주는 항목, P2는 유지보수와 재현성을 개선하는 항목이다. 같은 P0라도 실행 복구 → 결제 차단·검증 → 고객 흐름 정상화 순으로 적용한다.

### F01. 실제 앱이 연결되지 않는 시작 파일

**근거:** `index.mts:8,26,31,41`, `app.mts:43,509`, `render.yaml:18`, `Dockerfile:79`.

`index.mts`는 bootstrap HTTP 서버를 열고 `/api/health*`에 200과 `status: starting`을 반환한다. 다른 API는 503이다. 파일 전체에 `app.mts` import, 실제 HTTP 서버 연결·교체가 없다. `app.mts`는 Express 앱과 Socket.IO가 연결된 `httpServer`를 export하지만, 지정된 시작 파일에서 사용하지 않는다. Render와 Docker 모두 이 시작 파일을 실행한다.

**재현:** 현재 시작 파일의 핸들러를 격리 실행했을 때 health=200, orders=503이었다. DB나 운영 서버 호출은 없다. 헬스체크 성공을 서비스 준비 완료로 해석하면 장애가 숨겨질 수 있다.

**개선:** 실제 `httpServer`를 한 번만 listen하는 실행 경로를 확립한다. 부팅 상태가 필요하면 동일 서버에서 준비 상태를 관리하거나 bootstrap에서 앱으로 명확히 전환한다. 단순 import만 추가하면 이미 점유한 포트와 충돌할 수 있으므로 서버 소유권도 함께 정리해야 한다. 종료 시 HTTP·Socket·DB 연결을 닫고 초기화 실패는 실패 종료 또는 명확한 준비 실패로 표시한다.

**완료 기준:** 배포와 동일한 시작 명령으로 health뿐 아니라 안전한 실제 API와 Socket.IO 연결을 확인한다. 초기화 중 readiness는 실패하고, 초기화 완료 후에만 성공한다. DI·라우터 초기화 실패도 준비 완료로 처리되지 않아야 한다.

### F02. 고객 입력만으로 결제 완료를 기록하는 공개 경로

**근거:** `routes/payments.js:66`, `controllers/paymentController.js:52`, `services/PaymentService.js:127,193,200`.

`POST /api/payments`에는 인증·매장 권한·주문 capability가 없다. 서비스는 요청의 `payment_method`가 cash 또는 point이면 결제를 DONE으로 저장하고 수입 원장과 주문 결제 상태를 갱신한다. 포인트는 `point_amount > 0`인 경우에만 차감하므로 `payment_method: point, point_amount: 0`으로 완료 경로에 들어갈 수 있다. 상품 가격을 서버에서 재계산하는 방어는 있으나 수납 사실이나 포인트 충당을 보장하지 않는다.

**영향:** 실제 수납되지 않은 거래가 완료 매출로 기록될 수 있다. 포인트가 사용되는 경우 요청자가 지정한 전화번호·키만으로 지갑을 찾아 차감하는 경계도 함께 점검해야 한다.

**개선:** 고객은 현금·이체 결제 요청을 만들 수 있도록 하되 수납 전에는 미결제로 유지한다. 현금 수납 완료는 권한 있는 직원에게 한정하고 매장 권한을 확인한다. 포인트 결제는 검증된 지갑 소유권, 양의 정수 차감액, 결제액 전액 충당 또는 명시적 혼합 결제 규칙을 강제한다. 완료·원장·포인트 변경은 같은 트랜잭션에서 수행한다.

**완료 기준:** 익명 고객의 수납 완료 시도, 0·음수 포인트, 타인 지갑 사용, 교차 매장 수납을 거부한다. 고객 현금 선택만으로 수입 원장에 반영되지 않아야 한다. 이미 발생한 데이터 여부는 별도 읽기 전용 대사로 확인한다.

### F03. CORS가 주문 권한 헤더를 차단

**근거:** `app.mts:68,70,101`, `frontend/src/api/orders.js:59,66,87,92,98`, `frontend/src/api/misc.js:89`, `frontend/.env.production`의 공개 API 주소 설정.

프런트는 `x-order-capability` 및 `x-reservation-capability`를 보내지만 서버 허용 헤더에는 없다. 첫 OPTIONS 미들웨어가 204로 바로 종료하므로 뒤의 cors 설정만 수정해도 해결되지 않는다. Render API 직접 호출 구성에서는 브라우저 preflight가 이를 차단한다.

**개선:** 실제 사용하는 주문·예약·지갑 capability 헤더를 하나의 상수로 관리하고 모든 CORS 경로에 적용한다. 초기 OPTIONS, cors 패키지, 하단 안전망의 중복 처리를 정리한다. 허용 origin 정책은 유지한다.

**완료 기준:** 다른 origin에서 주문 준비·승인·분할결제·예약 조회를 브라우저로 수행한다. OPTIONS 성공뿐 아니라 허용 헤더와 실제 요청 완료를 확인하고 비허용 origin은 차단한다.

### F04. 같은 사용자 주문이 두 번 생성됨

**근거:** `frontend/src/pages/MenuPage.jsx:500,530,531`, `services/PaymentService.js:153`.

메뉴 화면은 먼저 `ordersAPI.create()`로 주문을 만든다. 현금·이체·매장카드에서는 이어서 `/payments`를 호출한다. 그 서비스는 기존 주문에 결제를 붙이지 않고 다시 `orders.create()`를 수행한다. 결제 방식에 따라 주문·결제 연결과 알림 대상이 달라져 대기 주문과 별도 결제 주문이 남을 수 있다.

**개선:** 기존 주문 ID와 capability를 받아 결제 요청을 생성하는 경로로 통일한다. 주문과 결제를 한 번에 생성하는 별도 기능이 필요한 경우 호출 계약과 권한을 분리한다. 고객 흐름은 하나의 주문 ID를 결제·추적·영수증까지 유지한다.

**완료 기준:** 현금·이체·매장카드 각각의 고객 클릭 한 번에 주문 한 건만 생성된다. 재시도에도 같은 주문에 연결되고 화면에서 추적하는 ID와 결제 레코드의 `order_id`가 같아야 한다.

### F05. 분산 환경에서 중복 요청이 동시에 통과

**근거:** `middleware/idempotency.js:30,44,50,92,113,127`, `utils/redisCache.js:156`.

현재 구현은 GET으로 처리 중 여부를 확인한 뒤 일반 SET을 비동기로 호출한다. 두 인스턴스가 동시에 캐시 미스를 읽으면 둘 다 처리된다. RedisCache는 SET NX를 사용하지 않으며 L1 캐시도 사용한다. 캐시 오류는 처리 진행으로 이어지고, 연결 종료 시 잠금을 지워도 비즈니스 작업이 계속될 수 있다. 키에 URL·주문·매장 같은 리소스 식별자가 없어 익명 namespace의 같은 키가 다른 리소스와 충돌할 여지도 있다.

**재현:** 두 Redis 조회가 모두 미스인 상황에서 같은 키의 동시 요청 두 개가 핸들러에 진입했다. 격리된 Redis 대역 재현이며 실제 Redis 클러스터 테스트는 아니다.

**개선:** 우선 결제·주문 작업의 영속 멱등 레코드와 유일 키를 DB에 둔다. Redis가 보조 잠금이면 `SET NX EX`로 원자 획득하고 소유자 토큰 확인 후 해제한다. 금융 작업의 캐시 장애 정책을 명시하고 실패 시 조용히 중복 처리하지 않게 한다. 응답 저장과 완료 전환, 장시간 처리, 연결 종료, 요청 바디 변경을 다룬다. 클라이언트는 같은 작업을 재시도할 때 같은 키를 유지한다.

**완료 기준:** 두 인스턴스·동일 키·50개 동시 요청에서 주문·결제·원장은 각 한 건이다. Redis 단절·프로세스 재시작·응답 유실 이후에도 같은 작업이 재실행되지 않는다. DB의 READY→DONE 조건부 갱신 방어는 유지하며 멱등 미들웨어 문제를 이유로 제거하지 않는다.

### F06. 포인트 잔액 갱신의 경쟁 상태

**근거:** `services/PointsService.js:345,351,355`, `config/prisma.js`의 트랜잭션 설정.

포인트 사용은 잔액을 읽어 확인하고 새 절대값을 UPDATE한다. 동일 잔액 스냅샷을 본 두 결제는 각각 성공해 차감 내역 합계와 잔액이 달라질 수 있다. `$transaction` 사용 자체는 이러한 경쟁을 해결하지 않는다. 현재 경로에 명시적 직렬화·행 잠금·잔액 조건부 차감은 확인되지 않았다.

**재현:** 두 호출이 100점의 같은 스냅샷을 읽고 각각 80점을 사용하면 거래 내역 차감 합계는 160점인데 저장 잔액은 20점이다. 이는 서비스 코드와 트랜잭션 대역의 재현이며 실제 PostgreSQL 동시 트랜잭션으로 추가 검증해야 한다.

**개선:** `id + 잔액 >= 사용액` 조건으로 원자적 decrement를 수행하고 갱신 건수 1을 확인한다. 또는 행 잠금·Serializable과 제한된 충돌 재시도를 적용한다. 사용자 식별자 검증, 차감액 범위, 차감 이벤트 유일성, 환불의 중복 방지도 함께 처리한다.

**완료 기준:** 잔액 100점에서 동시 80점 결제 두 개 중 한 개만 성공한다. 잔액과 포인트 원장이 항상 일치하며 환불 재전송도 한 번만 복구한다.

### F07. 테스트·배포 경로의 단절

**근거:** `.github/workflows/ci.yml:283`, `.github/workflows/playwright.yml:48`, `render.yaml:20`.

두 E2E 워크플로우는 존재하지 않는 `node index.js`를 실행한다. 기본 CI는 시작 파일의 실제 서비스 제공 여부를 확인하지 않으므로 F01이 통과할 여지가 있다. Render Blueprint는 `autoDeploy: true`이고 별도로 CI 이후 deploy hook도 존재한다. 설정 그대로 적용하면 provider의 Git 자동 배포가 검증 완료 이전에 시작될 수 있다. 실제 Render 대시보드의 활성 설정은 확인하지 않았다.

**개선:** 배포와 같은 명령으로 서버를 시작하는 smoke를 필수 PR 검사에 추가한다. Git 자동 배포와 검증 후 hook 중 하나를 명확히 선택하고 해당 커밋의 필수 검사 성공을 배포 조건으로 강제한다. 마이그레이션은 중복 실행·잠금·이전 버전 호환성을 포함해 한 경로로 통제한다.

**완료 기준:** 테스트 실패 커밋은 배포되지 않는다. 한 커밋이 한 번만 배포되고 실제 API smoke가 필수 게이트를 통과한다. 운영과 CI의 시작 파일·Node 조건이 동일해야 한다.

### F08. 결제 증빙의 저장·접근 정책 부재

**근거:** `routes/payments.js:15,17,21,29`, `controllers/paymentController.js:154`, `app.mts:425`, `render.yaml`의 STORAGE_DRIVER 설정.

증빙은 `public/uploads/proofs`에 직접 저장되고 공개 URL로 반환된다. Express가 public 전체를 인증 없이 제공한다. URL을 알면 다운로드 가능하며 파일명은 결제 ID와 시각 조합이다. Supabase 저장소 설정과 무관하게 이 경로는 로컬 디스크를 사용하므로 재배포 시 유실될 수 있다. MIME 문자열만으로 이미지 여부를 판단한다.

**개선:** 비공개 객체 저장소로 옮기고 매장 권한 또는 주문 권한 확인 후 짧은 유효기간의 접근 URL을 제공한다. 랜덤 키, 실제 파일 형식 검사·안전한 이미지 재인코딩, 보존 기간과 삭제 정책을 적용한다. 기존 공개 증빙은 존재 여부를 확인한 뒤 이전·접근 통제를 계획한다.

**완료 기준:** 익명 직접 조회는 실패하고 타 매장은 접근할 수 없다. 재배포 후에도 파일이 남으며 허용 형식 외 파일은 거부한다.

### F09. 보안 검사의 실패가 배포 차단으로 연결되지 않음

**근거:** `.github/workflows/security.yml:56,71`, `package.json:53`, `.github/workflows/ci.yml`의 security-scan·deploy 조건.

npm audit 실패는 `|| true`로 무시되고 high/critical 발견 시 경고만 출력한다. 검사는 수동·주간 실행이며 필수 deploy 의존성에 포함되지 않는다. 백엔드 Semgrep 명령은 없는 `app.js/index.js`를 대상으로 명시하고 실제 `app.mts/index.mts`는 대상 목록에서 빠져 있다. 루트 npm audit만 실행하여 별도 프런트 lockfile의 의존성을 충분히 확인하지 못한다.

**개선:** 새 진입점과 실제 코드 경로를 스캔하고 루트·프런트 의존성을 각각 검사한다. high/critical은 실패 종료하되 필요한 예외는 만료일·책임자·보완 통제를 기록한다. 스캐너 오류나 결과 파싱 실패도 검사 통과로 처리하지 않는다. 보안 검사를 필수 체크와 배포 게이트로 연결한다.

**완료 기준:** 고위험 테스트 fixture 또는 안전한 검사 실패 시 배포가 차단된다. 누락된 진입점과 프런트 lockfile을 검사한 증거를 저장한다. 본 분석에서는 취약점 레지스트리를 조회하지 않았으므로 현재 취약점 건수를 주장하지 않는다.

### F10. 마이그레이션에 뒤처진 검증 범위

**근거:** `tsconfig.json`, `eslint.config.js`의 `files: ['**/*.js']`, `jest.config.js`의 collectCoverageFrom·threshold, `.github/workflows/ci.yml`.

백엔드 strict=false이고 allowJs/checkJs가 꺼져 있다. 일반 JS 코드는 타입 검사 대상이 아니다. 린트는 JS를 대상으로 하여 TS/MTS 진입점이 검사되지 않는다. 커버리지는 JS만 수집해 TS/MTS 소스가 분모에서 빠진다. 라우트 statements 6%, Repository 4% 등의 임계값은 설정상 하한이며 현재 실측 커버리지 수치가 아니다. 같은 역할의 JS/TS 파일이 공존하여 실행 코드와 검증 코드가 달라질 가능성이 있다.

**개선:** 결제·포인트·권한의 실제 실행 소스를 기준으로 TS/JS 규칙과 커버리지 분모를 맞춘다. TS 전환은 파일 이름 변경이 아니라 단일 실행 소스와 타입 검증 확보를 완료 기준으로 삼는다. 전체 수치부터 올리기보다 금액 변조·교차 매장·중복 처리·동시 차감·환불·시작 명령의 핵심 시나리오를 필수 검증한다.

**완료 기준:** 핵심 실행 파일이 린트·타입·커버리지 또는 의미 있는 통합 검증에 포함된다. 변경된 코드의 검사 범위를 CI가 확인하고 실제 수치에 기반해 임계값을 단계적으로 올린다.

### F11. PDF 폰트가 Docker 런타임에 없음

**근거:** `services/ReportPdfService.js:8,54,271`, `fonts/`, `Dockerfile`의 production COPY 목록.

소스에는 폰트 탐색·등록과 폴백 로직이 있다. 그러나 Docker production 단계에는 fonts 디렉터리를 복사하지 않는다. 따라서 이미지 배포에서는 Helvetica 폴백으로 한글 출력 문제가 발생할 수 있다. Node 직접 배포와 Docker 배포의 결과가 달라진다.

**개선:** 필요한 폰트를 이미지에 포함하고 글리프 지원을 확인한다. 현재 NotoSans 파일명의 존재만으로 한글 지원이 입증되지는 않는다. PDF 생성은 쓰기 가능한 임시 경로·다운로드 후 정리·날짜 입력 검증도 함께 점검한다.

**완료 기준:** 실제 production 이미지에서 한글 매장명·상품명·일본어·중국어 예시를 PDF로 생성해 열어 확인한다. Render 직접 배포 결과와 비교한다.

### F12. 재현 가능한 개발·빌드 기준 부재

**근거:** `frontend/package.json`, `package.json`의 build/test 스크립트, README·CLAUDE 문서, CI 설치 명령.

프런트는 pnpm을 선언하지만 빌드·CI는 npm을 사용한다. build에 npm install이 섞여 있고 legacy-peer-deps 사용 여부도 다르다. 프런트 typecheck 스크립트는 있지만 프런트 자체 devDependencies에는 typescript가 없다. 현재 환경에서 npm run typecheck는 tsc를 찾지 못했다. 루트 컴파일러로 프런트를 직접 검사한 실행은 종료 코드 0이었다. 따라서 타입 오류와 도구 설치 누락을 구분해야 한다.

백엔드 테스트 스크립트의 POSIX 환경 변수 할당은 Windows 기본 셸에서 이식성이 없다. 문서는 `index.js/app.js`, 구버전 라우터 수·React Router 버전, Cloudflare/Vercel 운영 토폴로지가 서로 다르다.

**개선:** 패키지 관리자를 하나로 정하고 lockfile 기반 clean install을 사용한다. 각 패키지는 자신이 실행하는 컴파일러·검사 도구를 명시적으로 의존한다. 설치와 빌드를 분리하고 이식 가능한 테스트 실행을 제공한다. README를 현재 진입점·실제 라우팅 버전·공식 배포 주소의 기준 문서로 통일한다.

**완료 기준:** 빈 환경에서 lockfile만으로 설치·타입 검사·테스트·빌드가 재현된다. Windows 개발 환경과 Linux CI가 같은 테스트 명령을 사용한다.

| 멀티테넌트 | 역할·권한을 중앙화하고 Repository에서 매장 scope를 명시 | 교차 매장 조회·수정·수납·증빙 접근 회귀 테스트 통과 |
| AI | 구현 여부보다 시간순 검증과 결과 품질·fallback·비용을 평가 | 예측 WAPE/MAE를 단순 기준 모델과 비교, 추천 전환율 실험, 매장별 호출 예산·timeout·fallback 기록 |
| 프런트 성능 | 주문 완료 흐름과 실제 기기 데이터를 기준으로 개선 | 매장 메뉴·장바구니·결제의 LCP/INP/CLS를 측정한 뒤 예산 합의; 로컬 화면만으로 수치 추정하지 않음 |
| 데이터 | 결제 완료와 원장·포인트 이벤트의 유일성, 상태 전이·보존 정책 적용 | DB 제약·대사 작업·환불 재시도·보존 기간 검증 |
| 검증 효율 | 정적 계약 검사 + 실제 시작 smoke + 금융 동시성 + 핵심 고객 E2E 조합 | 겉보기 green이 실제 서비스 불가를 숨기지 않음; 실패 원인이 재현 가능한 로그·산출물로 남음 |

기능 추가의 투자 판단은 먼저 안정적인 결제 완료율·주문 중복률·매장 운영 오류를 측정한 뒤 내리는 것이 적절하다. 기존 구성에는 가격 재검증, 매장 권한 검사, 조건부 결제 상태 변경, 마스킹 등 유용한 방어가 이미 있으므로 이를 보존하면서 실행 경로와 남은 경계를 보강한다.
