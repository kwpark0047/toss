# 역할 API 변경 영향 분석

일반 주문 상세 조회는 kitchen 역할의 허용 목록에서 제외한다. 조리 직원은 최소 필드만 제공하는 KDS API를 사용한다. 기존 고객 주문 접근 토큰과 소유자/매니저 권한은 유지한다. 비활성 직원 배정은 내 매장 목록에서도 제외한다. 신규 주문번호의 날짜 접두사는 UTC가 아닌 한국 날짜를 사용하며 기존 번호를 변경하지 않는다.

주방은 조리 조회/진행만 수행하고 수납·환불은 수행하지 않는 정책으로 분리한다. 관리자/매니저의 기존 수납·환불은 유지하고 일반 직원은 수납만 허용한다. controller의 중복 권한표를 공통 storeAuth 권한표로 통일한다.

KDS 응답의 고객 전화번호·이름·FCM 토큰·Toss 식별자·배송주소는 조리에 필요하지 않아 제거한다. 조리 화면에는 연락처 등록 여부만 제공한다. 현재 KitchenDisplay는 phone 마지막 네 자리 표시 외에는 이 필드를 사용하지 않는다. 외부 KDS 소비자는 신규 has_customer_contact를 사용해야 한다. 주문 ID·번호·상태·아이템·가격·메모·테이블·시간·대기번호는 유지한다.

KDS cancelled 상태 쓰기는 OrderService.cancelOrder의 재고 복원 및 결제/환불 확인을 거치지 않는다. 현재 KitchenDisplay는 preparing/ready/completed만 호출하며 cancelled 호출자는 검색상 없다. cancelled 직접 쓰기는 409로 차단하고 기존 관리자 주문 취소 API를 사용해야 한다. 기존 외부 클라이언트에 이 제한을 공지하고 오류 처리를 확인해야 한다. 운영 배포는 아직 수행하지 않는다.
