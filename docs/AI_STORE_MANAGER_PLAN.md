# WeMarket AI 매장 매니저 기획안

작성일: 2026-10-07 · 범위: 추가 기능 기획, 코드·운영 DB 변경 없음

## 1. 제품 목표

매장 데이터를 읽고 오늘의 문제를 발견하며 실행 가능한 개선안을 제안하고, 사장님이 실행한 결과를 검증하는 디지털 매장 매니저다. 사장님이 매일 확인할 핵심 질문은 네 가지다.

1. 오늘 무엇이 문제인가?
2. 어떤 메뉴를 추천해야 하는가?
3. 언제 누구에게 어떤 프로모션을 해야 하는가?
4. 지난 제안이 실제로 도움이 되었는가?

첫 화면은 지표 나열보다 오늘 해야 할 일 최대 3개를 우선한다. 모든 제안에는 근거, 데이터 기준 시각, 실행 방법, 비용 또는 제약, 평가 기간이 붙는다. 채팅은 근거를 묻거나 조건을 변경하는 보조 수단이다.

## 2. 기존 프로젝트 활용과 부족한 데이터

아래는 소스 코드에서 확인한 구조다. 실제 수집량·외부 공급자 연결 완료를 뜻하지 않는다.

| 영역 | 기존 기반 | 매니저를 위해 필요한 보완 |
|---|---|---|
| 통합 매출 | StoreIntegrationService, integration_events의 금액·환불·취소·주문 중복 처리 | 영업일·시간대별 스냅샷, 수집 지연 표시, 채널별 상세 분석 |
| 자체 주문 | orders와 주문 상세 | QR·모바일·키오스크 유입을 명시적으로 구분; 현재 통합 집계에서는 자체 주문을 qr로 묶음 |
| 외부 주문 | CSV·인증 API 공통 계약 | 현재 계약에 메뉴 품목·수량·원가가 없음. 외부 메뉴별 추천에는 주문 라인과 메뉴 매핑 추가 필요 |
| 고객·CRM | store_customers, RecommendationContextService, CrmAutomationService | 분석 대상과 광고 수신 가능 대상을 구분; 고객 참조값만으로 동일 인물 단정 금지 |
| 추천 성과 | RecommendationTrackingService, 노출·클릭·전환·일별 통계 | 고객용 추천과 사장님용 제안을 구분하고 action_id와 실행 결과 연결 |
| 리뷰 | 자체 리뷰, 네이버 플레이스 정보 연결 | 자체 리뷰부터 분석. 네이버 지역검색 키로 리뷰 본문 수집 불가 |
| 외부 상황 | 공통 서울 데이터·기상청 인증 설정 | 실제 설정·최신 관측 여부 확인. 서울 인허가 데이터를 유동인구 데이터로 해석하지 않음 |

재고·원가·품목 매핑이 없으면 재고 소진 또는 고마진 추천은 제공하지 않는다. 연결되지 않은 배달·POS 데이터는 매출 0으로 표시하지 않고 미연결로 표시한다.

## 3. 네 가지 핵심 기능

### 오늘의 문제 발견

같은 요일·같은 영업 시간대의 최근 4~8주를 기준으로 순매출, 결제 주문 수, 객단가, 취소·환불 비율을 비교한다. 오늘 진행 중인 시간은 기준일의 동일 시각까지 비교한다. 매장 시간대와 자정 이후 영업일 경계를 반영한다.

초기 탐지 규칙은 비교 가능한 과거 구간 4개 이상, 해당 지표에 충분한 주문 수가 있을 때만 적용한다. 주문 수 30건과 매출 하락 20%는 초기 튜닝 후보이며 매장 규모별로 검증한다. 취소율은 소량 주문에서 과도하게 경고하지 않도록 최소 모수와 증가 폭을 함께 본다. 동일 문제는 묶어서 한 번만 알리고 상태가 악화되었을 때 갱신한다.

출력: 문제 → 근거 → 가능한 원인 → 확인할 사항 → 대응 제안. 가격 변경·휴점·수집 중단을 확인하기 전에는 매출 하락의 원인을 단정하지 않는다. 문제없으면 "현재 확인된 주요 이상은 없습니다"라고 설명한다.

### 오늘의 메뉴 추천

자체 주문의 판매량·동반 구매·시간대 수요·판매 가능 여부부터 활용한다. 품절·숨김 메뉴를 제외한다. 원가가 있으면 공헌이익을 고려하고, 원가가 없으면 판매량 또는 매출 기준이라고 명시한다. 재고가 최신일 때만 재고 소진 목표를 사용한다.

제안별로 추천 메뉴, 추천 이유, 노출 위치, 적용 시간, 목표 지표를 제시한다. 예: QR 메뉴 첫 화면에 노출하기, 관련 메뉴에 추가 추천하기, 세트 구성 초안 만들기. 사장님이 미리보기 후 적용한다.

### 시간대 프로모션

주문이 적은 시간대와 매장 처리 여유를 함께 확인한다. 원가·할인 비용·예산을 알면 수익 기준으로 할인 상한을 제시한다. 모르면 손익분기 할인율을 계산하지 않으며 무할인 메뉴 노출 실험 또는 원가 입력을 우선 제안한다.

대상 시간, 메뉴, 고객군, 할인/혜택, 기간, 예산 상한, 중단 조건, 성공 기준을 하나의 실행안으로 만든다. 할인·문자 발송·쿠폰 발급은 기존 승인 흐름에 연결하며 실제 광고 발송은 동의·제공기관 설정·차단 대상 확인 후 실행한다. 주문 처리능력 데이터가 없으면 혼잡도를 추정 사실처럼 표현하지 않는다.

### 지난 추천 효과 검증

제안 열람·승인·예약·실행·실패·중단·평가를 모두 기록한다. 승인은 실행 성공과 다르다. 실행 API 결과와 실제 주문·쿠폰 사용·메뉴 노출 데이터를 연결한다.

기본 평가 기간은 시간대 프로모션 7일, 메뉴 구성 14일의 후보값이다. 같은 요일·시간대의 비교 기간을 사용하고 운영시간·휴일·날씨·가격 변경·수집 누락을 표시한다. 목표 표본 미달이면 기간 연장 또는 판단 보류다.

통제군이 없으면 "실행 후 관측 지표가 개선되었습니다"라고 말하며 인과효과를 단정하지 않는다. 충분한 표본과 추적이 확보된 경우 고객군 또는 QR 노출 단위로 실험군·대조군을 배정하고 효과 및 불확실성 범위를 보고한다. 쿠폰 사용 주문의 매출 전체를 추가 매출로 계산하지 않는다.

## 4. 화면과 대화 경험

관리자 메뉴에 "AI 매장 매니저"를 추가한다. 모바일에서는 카드 한 장씩 읽고 실행할 수 있도록 한다.

- 오늘의 브리핑: 데이터 기준 시각, 주요 문제 3개 이하, 우선순위와 근거.
- 실행 제안: 메뉴·시간대·고객군, 미리보기, 비용/예산, 성공 기준, 적용 또는 수정.
- 진행 중: 예약/실행 상태, 중단 버튼, 실패 원인 및 재시도 가능 여부.
- 효과 보고: 관측 개선/악화/불확실, 비교 구간, 주문 모수, 비용과 성과.
- 매니저와 대화: "왜 추천했나요?", "할인 없이 해주세요", "배달은 제외하세요" 등 현재 매장과 조회 기간 안에서 답변.

브리핑 생성은 영업 전 기본 1회, 이상 변화는 필요한 경우만 갱신한다. 알림은 앱 내부부터 시작하고 사장님이 빈도·조용한 시간대를 설정한다. 외부 알림 채널은 선택 기능이다.

다음 대화는 제품 표현 예시이며 실제 매장 분석 결과가 아니다.

> 사장님, 오늘 14~16시 주문 수가 같은 요일 비교 구간보다 적습니다. 다만 POS 수집이 지연되어 자체 주문 기준으로만 확인했습니다.

> 이 시간대에는 A 메뉴를 먼저 보여주는 실험을 추천합니다. 자체 주문에서 함께 구매되는 비율이 높습니다. 원가가 없어 수익 증가는 아직 계산하지 않았습니다.

> 할인 없이 QR 메뉴 첫 화면에 7일간 노출해보세요. 적용 화면과 평가 기준을 확인한 뒤 실행할 수 있습니다.

> 지난 제안 실행 후 A 메뉴 주문 비중이 높아졌습니다. 대조군이 없어 제안의 효과라고 확정할 수는 없습니다. 다음에는 노출 실험으로 검증해보겠습니다.

## 5. 분석과 AI 역할 분리

처리 흐름: 매장별 수집 → 정규화·중복 제거 → 데이터 품질 검사 → 지표 스냅샷 → 규칙/통계 분석 → 실행안 생성 → AI 설명 → 사장님 승인 → 실행 → 성과 평가.

수치·비용·비교·권한은 서버에서 계산한다. AI는 검증된 지표와 실행 후보를 이해하기 쉬운 문장으로 설명하고 질문에 답한다. AI가 자유 SQL을 실행하거나 임의 할인·발송을 수행하지 않는다. 출력은 구조화 스키마와 실제 메뉴/캠페인 ID로 검증한다. 근거 없는 수치가 있으면 재생성 또는 규칙 기반 문장으로 대체한다.

각 지표에 source, as_of, coverage, quality를 기록한다. 주문 수·연결 수·미연결 채널·수집 지연·메뉴 매핑률을 표시한다. 신뢰 수준은 확인된 조건으로 설명하며 근거 없이 AI 확률을 붙이지 않는다. 기상청 대체값은 실제 날씨 근거로 사용하지 않는다. AI 장애 시 검증된 규칙 기반 브리핑을 제공한다.

## 6. 저장 구조와 API 제안

기존 고객용 ai_recommendations와 성과 테이블을 그대로 매니저용으로 해석하지 않는다. 아래는 신규 설계안이며 실제 마이그레이션은 구현 시 별도 검토한다.

| 제안 테이블 | 주요 내용 |
|---|---|
| store_metric_snapshots | store_id, 영업일·시간대, 지표, 비교 기준, 수집 범위·품질·시각, 버전 |
| manager_insights | 문제/기회, 근거 스냅샷, 중요도, 유효기간, 중복 방지 키 |
| manager_actions | insight_id, 메뉴/프로모션 실행안, 상태, 승인자, 실행 idempotency_key, 예산·중단 조건 |
| manager_action_events | 승인·예약·실행 성공/실패·중단 이력, 기존 캠페인·메뉴 설정과 연결 |
| manager_evaluations | action_id, 목표 지표, 비교군·기간, 관측 결과·추정 효과, 비용, 표본, 판정 근거 |

모든 조회·실행은 store_id와 매장 역할을 서버에서 검증한다. 원본 스냅샷을 고정해 이후 데이터 변경과 판단 당시 근거를 구분한다. 실행은 동일 작업의 중복 적용을 차단하고 실패 재시도가 이중 쿠폰·발송으로 이어지지 않게 한다.

API 후보: GET /api/stores/:storeId/manager/briefing, GET insights, POST actions/:id/approve, POST actions/:id/execute, POST actions/:id/stop, GET actions/:id/evaluation, POST manager/chat. 실행·승인은 서버 검증된 소유주 권한을 기본으로 하고 직원은 허용된 조회만 제공한다.

LLM에는 전화번호·API 키·결제 인증정보를 보내지 않는다. 고객 데이터는 집계 또는 가명 참조값으로 최소화한다. 리뷰·CSV는 분석할 외부 데이터로 취급하고 포함된 지시문이 실행 권한으로 이어지지 않게 한다. 다른 사업자의 데이터를 섞어 분석·학습하지 않는다.

## 7. SaaS 상품화

요금 변경 없이 기존 구독 기능의 추가 모듈로 먼저 제공한다. 매장별 사용 가능 여부, 일일 생성·채팅 한도, 캐시, ai_usage_logs 비용 집계를 연결한다. 이후 브리핑, 실행/CRM, 다매장 비교 등 기능 단위 상품화를 검토하되 이번 기획에서 가격을 확정하지 않는다.

재방문·매출 상승을 보장하지 않는다. 사용자 가치는 브리핑 열람보다 실행된 개선안, 평가 가능한 실험, 검증된 비용 대비 성과로 판단한다.

## 8. 단계별 구현과 완료 기준

### 1단계: 읽기 전용 매니저

자체 주문·메뉴·고객·자체 리뷰와 통합 매출로 오늘 브리핑, 이상 탐지, 메뉴/시간대 제안을 제공한다. 데이터 부족 상태와 조회 기준을 명확히 표시한다. 새 DB 설계·승인 후 구현한다.

완료 기준: 표시 수치가 원장/주문 집계와 일치, 매장 간 조회 차단, 늦은 환불·취소 반영, 수집 중단을 매출 하락으로 오인하지 않음, AI 오류 시 기본 브리핑 제공.

### 2단계: 승인 후 실행

메뉴 노출·프로모션·기존 CRM 캠페인을 미리보기 후 실행한다. 예약·예산 상한·중단·실패 복구를 지원한다.

완료 기준: 승인 없는 실행 없음, API 재시도 시 중복 실행 없음, 실제 실행 상태 추적, 잘못된 메뉴/매장 적용 차단, 동의 없는 광고 대상 제외, 실패를 성공으로 보고하지 않음.

### 3단계: 성과 학습

실행안과 주문·쿠폰·추천 노출을 연결해 평가하고, 실험이 가능한 매장부터 대조군 검증을 도입한다. 성공/실패/불확실 결과를 다음 추천 우선순위에 반영한다.

완료 기준: 관측 변화와 인과 추정 구분, 표본 부족 시 판단 보류, 취소/환불/할인비용 반영, 평가 근거 재현, 동시에 진행된 캠페인의 기여도 중복 계산 방지.

### 4단계: 외부 채널 정밀 분석

업체 API·품목 상세와 메뉴 매핑, 검증된 원가·재고를 확보한 매장부터 POS·배달·키오스크를 확장한다. 업체별 계약과 실제 API 범위 확인 후 개발한다.

## 9. 권장 첫 출시 범위

매장별 오늘 브리핑 + 자체 주문 기준 메뉴/시간대 제안 + 실행안 저장 + 사장님 피드백을 먼저 출시한다. 효과 검증은 평가 가능한 실행부터 제공하고, 데이터가 부족하면 "지난 추천은 실제로 효과가 있었습니다"라는 확정 문장을 사용하지 않는다.

첫 파일럿은 영업일·주문 데이터가 충분한 매장부터 진행한다. 제안 채택률, 실행 성공률, 평가 가능 비율, 오경보율, AI 비용/매장을 함께 확인하여 확대 여부를 판단한다.
