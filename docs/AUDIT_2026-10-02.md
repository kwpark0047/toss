## 1. 반영 완료 (검증됨)

### 1.1 JWT algorithm 고정 — `middleware/auth.js`

`jwt.verify()`가 `algorithms`를 지정하지 않아, 같은 `JWT_SECRET`으로 만든
HS384/HS512 토큰이 **인용됨**. 알고리즘 혼동 공격에 열려 있었다.

**조치**: 두 `verify` 호출(29행 `authMiddleware`, 48행 `optionalAuth`)에
`{ algorithms: ['HS256'] }` 추가.

**재현 검증** (`tests/unit/middleware/authAlgorithms.test.js`, 실제 crypto 사용)
| 토큰 | 조치 전 | 조치 후 |
|------|---------|---------|
| HS256 access | 통과 | 통과 (회귀 없음) |
| HS384, 같은 secret | **통과 (취약)** | 401 거부 |
| HS512, 같은 secret | **통과 (취약)** | 401 거부 |
| `alg=none` | 거부 | 거부 |

`alg=none` 은 jsonwebtoken 자체 기본 동작으로 원래부터 차단됐다. 실질 방어 효과는
HS384/HS512 차단이다.

**sign site 조사 결과** (`authController`·`socialAuthController`·`admin2faController`)
3곳 모두 `algorithm` 미지정(= jsonwebtoken 기본 HS256) → **호환성 깨짐 없음**.

### 1.2 인바운드 Toss webhook dedup — 도입하지 않음

`webhook_deliveries` 테이블에 dedup 키가 있으나 이는 **아웃바운드 발신**용.
인바운드 경유는 `paymentLimiter`가 `/api/payments` 전체에 10req/60초로 제한하고
운영 제한이 기존 주문Webhook 대비 낮아, 유효 webhook이 정상 처리 중에 429로
배제될 위험이 있다. 근거 없이 dedup을 넣지 않았다.

### 1.3 죽은 파일 정리 — 3개 삭제

`middleware/rateLimiter.ts` · `middleware/validate.ts` · `utils/aiRateLimiter.ts`
import 0개이며 동일 경로 `.js`가 라이브다. 삭제 후 문서 참조 2곳 정리.

### 1.4 `getFilteredCustomers` DB 레벨 제한

기존 `take` 없는 전체 조회 후 `slice(0,100)` 폐기 → DB→Node 메모리→폐기 구간에서
OOM/지연. `take: 100` + 동일 조건 `count()` 병렬 실행으로 교체.
`{ count, hasMore, customers }` 반환. 프런트(`BulkSMSManager.jsx`)는
`customers`만 사용하므로 하위 호환.

> `sendBulkSms` 전체 조회와 `getCustomerAnalysis` 전체 조회는 **의도된 동작**이므로
> 변경하지 않았다. 장기적으로 job queue 필요.

## 2. 반영하지 않기로 결정 (근거 있음)

### 2.1 JWT `issuer` / `audience` 검증 — 도입하면 전 사용자 로그아웃

verify 에만 `issuer`/`audience` 를 추가하면, **지금까지 발급된 모든 토큰**이
검증에 실패한다. 3개 sign site 어디에도 `iss`/`aud` 가 없기 때문이다.
적용하려면 sign site 3곳 동시 변경 + 토큰 재발급 순서가 선행되어야 한다.
단독 변경은 서비스 장애이므로 보류했다.

### 2.2 `issuer`/`audience` 와 별개로, refresh 토큰 격리는 이미 충분

access=`JWT_SECRET`, refresh=`JWT_REFRESH_SECRET` 로 **서명이 다름**.
따라서 refresh 토큰은 `JWT_SECRET` 으로 verify 자체가 실패한다.
추가로 `type !== 'access'` 검사까지 있어 이중 방어다.

> `utils/orderCapability.js` 는 `ORDER_CAPABILITY_SECRET` 미설정 시 `JWT_SECRET` 으로
> fallback 하지만 payload `type: 'order_capability'` 이고 verify 가 `access` 만
> 허용하므로 `authMiddleware` 를 통과하지 못한다.

## 3. 잔여 위험 (미조치 — 근거만 확보, 임의 변경 금지)

### 3.1 죽은 레이어가 암호화되지 않은 결제 라우터를 보유 — 심각도 높음(잠재)

`app/interfaces/http/paymentRouter.js` 는 `app.mts` 에 **mount 되어 있지 않다**.
`paymentRouter`·`orderRouter`·`storeRouter`·`customerRouter` 는 구조 테스트와
`scripts/test-clean-arch.js` 에서만 로드된다. `monitoringRouter` 만 실제 mount.

따라서 **런타임에 결제 경로가 이중 등록된 것은 아니다.** 실제 경로는
`routes/payments.js` → `controllers/paymentController.js` 이다.
DI 컨테이너는 test/production 모두에 mount 되므로
`application/payments/*` use case 클래스는 **인스턴스화되지만 HTTP 로 도달 불가**다.

**잠재 위험**: `paymentRouter.js` 에는 인증·idempotency 미들웨어가 하나도 없다.
누군가 "연결 누락"을 고치려고 mount 하면 인증 없는
`POST /processPayment`·`POST /:id/confirm`·`POST /:id/cancel` 이 노출된다.
**mount 금지**, 또는 삭제·보호 대상으로 결정 필요.

### 3.2 죽은 webhook dispatcher 중복 — 심각도 중간

- `services/WebhookDispatcherService.js` (619줄): import 0개. 죽음.
- `services/webhookDispatcher.js`: 유일한 라이브 구현.
  (`v1Controller.js`, `OrderService.js` 사용)

라이브 정책 — timeout 8초, 최대 5회, backoff 1/5/30/120/360분, **jitter 없음**.
여러 스토어가 동시에 실패하면 재시도 시각이 겹쳐 스파이크가 될 수 있다.
대량 삭제에는 구조 테스트 fixture 영향이 있어 승인 없이 손대지 않았다.

### 3.3 `orderCapability` 토큰의 secret fallback

`ORDER_CAPABILITY_SECRET` 미설정 시 `JWT_SECRET`/`NEXTAUTH_SECRET` 으로 fallback.
전용 시크릿을 운영에서 반드시 설정해야 한다(3.1 경로가 드러난 대로).

### 3.4 문서 정확도

`COVERAGE_IMPROVEMENT_PLAN.md` 는 실제 `.js` 를 대상으로 쓰인 커버리지 문서인데도
다수 `.ts` 경로를 열거한다(삭제로 직접 발생시킨 2곳은 수정). 나머지는
문서화 결함이며 이번 diff 범위를 넘어선다.

### 3.5 불가 확인 항목

- 배포 상태: `https://wemarket.onrender.com/api/health` 가 연결 후 15~20초 응답 없이
  HTTP `000`. Render CLI 토큰·`gh` CLI 부재로 배포 로그/원인 직접 조회 불가.
- Toss 이벤트별 서명 필수 계약: 공식 문서 기준으로 확정하지 못함.
  HMAC timestamp 허용차 300초는 `middleware/tossWebhookAuth.js:66` 기준.
- `semgrep@^0.0.1` 은 binary 없는 스텁 → `security:scan` 이 exit 127. 정적 보안 스캔 미실행.

### 프런트 CSRF — 검증 완료 (환경 문제였음)

`frontend/src/lib/csrf.test.js` 는 처음에
`[vitest-pool]: Failed to start forks worker` → `Timeout waiting for worker to respond`
로 수집에 실패했다. **테스트 코드 문제가 아니라 실행 환경 문제임을 확인했다.**

- Vitest config·jsdom·`src/test/setup.js` 는 모두 정상 존재.
- `forks` / `threads` / `vmThreads` / `vmForks` **4개 pool 전부 동일하게 실패**.
- 심지어 `expect(1+1).toBe(2)` 3줄짜리 트리비얼 테스트도 `--environment=node` 에서
  동일하게 멈췄다 → 코드와 무관.
- 원인: WSL 에서 프로젝트가 Windows 드라이브(`/mnt/d`, 9p/DrvFs 마운트)에 있고,
  Vitest 워커 부팅 시 IPC 가 응답하지 못한다. `Duration: 60.23s` 로 고정 60초 타임아웃.
- **해결 확인**: 동일 파일을 네이티브 Linux fs(`/tmp`)로 복사해 동일 `node_modules` 를
  재사용하니 **23/23 통과**. → 테스트 코드·로직은 정상, `npm test` 는 정상 환경에서 실행된다.

즉 프런트 CSRF 모듈은 별도 하네스 없이도 실제 Vitest 로 23건 검증되었다.
