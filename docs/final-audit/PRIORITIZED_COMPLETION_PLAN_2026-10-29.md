## 3. 중복을 제거한 우선순위

### P0 — 서비스가 로그인·가입을 안정적으로 제공하는지 확정

**통합 과제:** Render 기동/DB 연결, API health, Vercel API 프록시, 로그인·가입 오류를 한 번의 동일 배포 검증으로 해결한다.

**이유:** health 503과 로그인 500/`42P05` 기록이 있다. 이후 단일 로그인이 성공했다는 사용자 확인은 간헐 장애가 해소됐다는 증거가 아니다. 고객이 로그인하지 못하면 다른 기능 검증도 의미가 없다.

**작업:**

1. Render 실제 서비스 ID·revision·기동 로그와 DB 연결 상태를 확인한다. 비밀값은 열람·복사·출력하지 않고 DB 프로젝트 참조만 대조한다.
2. Render와 Vercel의 `/api/health`가 각각 JSON `status=ok`, `db=connected`를 반환하는지 확인한다. Vercel은 앱 HTML/404가 아닌 백엔드 JSON이어야 한다.
3. 최근 `42P05`를 격리 환경에서 재현한다. transaction pooler와 Prisma 연결 옵션, 준비된 statement 사용 방식이 원인인지 검증하고 수정한다. 단순 재시도나 오류 숨기기로 끝내지 않는다.
4. 가입·로그인·로그아웃·새로고침 후 세션 유지·잘못된 비밀번호·중복 계정을 테스트 계정으로 검증한다.

**완료 기준:** cold start 포함 연속 10회 health 요청 모두 올바른 JSON과 DB 상태를 반환하고, 동일 환경에서 로그인/로그아웃 핵심 시나리오 20회 연속 성공하며 5xx·CORS·세션 유실이 0건이다. 테스트한 Render/Vercel revision이 기록된 RC SHA와 일치한다.

### P1 — 운영 DB 대상·마이그레이션 이력·복구 가능성 정합화

**통합 과제:** Render DB 대상 대조, Prisma/실제 스키마 이력 대사, 백업 복원 검증을 하나의 DB 안전성 게이트로 묶는다.

**이유:** 기존 DB 감사는 프로젝트 참조가 일부 확인됐지만, DB 이력은 46행이었던 스냅샷과 현재 로컬 49개 migration 디렉터리 사이에 차이가 있다고 기록했다. 실제 스키마가 일부 변경을 이미 포함하더라도 Prisma journal을 임의로 `resolve`하거나 migration을 바로 적용하면 이력·스키마가 더 어긋날 수 있다.

**작업:**

1. 승인된 운영 설정에서 `DATABASE_URL`, `DIRECT_URL`, `MIGRATION_DATABASE_URL`의 프로젝트 참조만 대조한다. 값 전체나 비밀번호는 보고서·채팅·로그에 남기지 않는다.
2. 실제 `_prisma_migrations` 행·checksum·unfinished/rolled-back 항목과 로컬 49개 migration, 현재 스키마 diff를 읽기 전용으로 비교한다. Supabase migration 이력과 Prisma 이력을 서로 같은 것으로 취급하지 않는다.
3. 차이별로 이미 적용됨/누락/수동 변경/불명으로 분류하고 적용 순서·영향·복구 절차를 준비한다. 운영 migration은 이 문서의 계획만으로 실행하지 않는다.
4. 복원 가능한 백업/PITR 시점과 보존 기간을 확인한다. 비용 없는 격리 PostgreSQL에서 백업을 복원해 핵심 테이블·관계·행 수를 확인하고 실제 복구 절차 및 소요 시간을 기록한다.
5. RLS 119개 활성/정책 0개라는 과거 결과를 테이블 그룹별로 검토한다. 앱 서버 DB 역할이 필요한 접근을 하는지, anon/authenticated가 계속 차단되는지 검증한다. 대량 정책 생성/비활성화는 하지 않는다.

**완료 기준:** 세 연결값의 대상이 합의된 DB와 일치하고, 스키마·Prisma journal 차이가 모두 설명되며, 적용할 migration이 있으면 별도 검토 가능한 plan과 복구안을 갖춘다. 격리 restore가 성공하고 최소 주문·사용자·매장 관계 검증 및 복구 시간/RPO/RTO가 기록된다.

### P1 — 같은 RC의 역할별 주문·수납·주방 회귀 E2E

**통합 과제:** 역할별 기능 테스트를 가입부터 주문·원장까지 하나의 staging 시나리오로 통합한다.

**작업:**

1. 운영과 분리된 DB·테스트 계정·테스트 webhook receiver를 지정하고 `test_run_id`로 fixture와 거래를 추적한다.
2. 사업자 가입 → 1개월 체험 → 관리자 승인/승인 취소 → 매장·메뉴 설정을 검증한다.
3. 사업자가 만든 매니저·직원·주방 계정의 권한 차이, 자기 매장 한정 조회, 직원 추가·삭제를 검증한다.
4. 고객 QR 접속 → 메뉴/옵션 → 장바구니 축소·복원 → 분할 결제 설정 → 현금 또는 계좌이체 주문을 검증한다.
5. 사업자/직원의 주문 접수·상태 전이 → 주방 KDS/Socket 업데이트 → 결제 확인 → 원장·매출 집계를 대사한다.
6. 중복 제출·동시 요청·네트워크 실패 후 재시도·권한 없는 매장 ID 변경을 넣어 주문/결제 중복과 tenant 침범이 없는지 확인한다.
7. AI 분석은 주문 데이터가 축적된 뒤 근거 기간·출처가 표시되는지, 데이터 부족 시 추측하지 않는지, 사업자 승인 전 실행되지 않는지 확인한다.

**완료 기준:** 모든 필수 역할 시나리오가 동일 RC SHA의 staging에서 통과한다. 주문 수·수납액·원장 순매출이 정확히 일치하고 중복 금전 효과·매장 간 데이터 접근·미승인 외부 실행이 0건이다. 50회 반복 시험을 주장하려면 격리 DB에 실제 50회 기록과 최종 대사표가 있어야 한다.

### P1 — 깨끗한 RC·배포 추적성·복구 게이트

**통합 과제:** 로컬 작업분과 증거 파일을 분리해 깨끗한 RC를 만들고 정확한 SHA를 CI·스테이징·운영에서 추적한다.

**현재 주의점:** 로컬 브랜치는 `origin/main`보다 3커밋 앞서 있고 `reports/`에 약 29,631개 미추적 파일이 있다. 민감정보 가능성이 있는 보고서, 스크린샷, JSON 증거, 임시 검증 파일이 혼재하므로 `git add -A`를 사용하지 않는다.

**작업:** 코드와 필요한 테스트·마이그레이션·정제된 문서만 선별한 RC를 만들고, 남은 자료는 비밀값·개인정보·운영 증거 여부를 확인한 뒤 분류한다. 정확한 RC SHA로 백엔드/프론트 빌드, 필수 CI, staging E2E를 완료한다. 배포 전후에 Vercel·Render revision과 smoke test 결과를 보관한다. 롤백은 직전 정상 SHA로 실제 복구 가능한지 staging에서 확인한다.

**완료 기준:** RC에 의도하지 않은 임시 파일·비밀값이 없고 작업 트리와 PR diff가 검토 가능하다. 필수 CI와 빌드가 정확한 SHA에서 통과하며, staging과 배포된 두 서비스가 같은 SHA를 사용하고 rollback 절차가 검증된다.

### P2 — 결제와 외부 연동을 계약 상태에 맞게 격리

**통합 과제:** 현금/이체 파일럿과 향후 Toss·카드 결제 검증을 명확히 분리하고, 업체 연동은 실제 데이터 대사를 기준으로 관리한다.

**작업:**

- Toss 계약 완료 전에는 카드/Toss 결제를 ‘개발 중’으로 표시하고 승인 요청을 차단한다. 현금/이체 주문은 별도 수납 확인 및 원장 대사로 staging 검증한다.
- sandbox를 실행할 때만 테스트 키·MID·webhook이 운영과 분리됐는지 먼저 확인한다. 승인·취소·중복·지연 webhook·원장 대사를 테스트한다.
- POS/배달/PG/공공 데이터는 업체별 API·CSV 원본을 확보한 뒤 주문번호·거래시각·매출·수수료·취소·입금액을 일별 및 주문별로 대사한다. “adapter 코드 있음”과 “업체 운영 검증 완료”를 별도로 표시한다.

**완료 기준:** 현금/이체 수납액과 원장 값이 일치한다. Toss/카드는 별도 sandbox 결과가 있을 때만 준비 완료로 바꾸며, 실제 상용 활성화는 계약 및 소유자의 별도 운영 승인 후 진행한다. 외부 provider는 실제 원본 데이터 대사 성공 전까지 운영 검증 완료로 표시하지 않는다.

### P2 — 운영 관측성·성능·장비와 접근성 검증

**통합 과제:** 관리 기능, QR 고객 흐름, 주방·프린터를 사용성·복구·부하 기준으로 한 번에 검증한다.

**작업:** health/readiness와 오류율을 분리하고 request/correlation ID, 민감정보 마스킹, 장애 알림을 확인한다. Render cold start 시간을 측정해 첫 로그인과 QR 메뉴 응답을 기록한다. 관리자·사업자·직원 화면은 375/768/1280px에서 확인하고, 키보드/스크린리더 기본 항목과 실제 주방 장치·프린터 출력은 가능한 기기에서 검증한다.

**완료 기준:** 주요 경로의 p95 응답 목표와 cold-start 한계가 제품 기준으로 문서화되고 측정 결과가 목표 안에 있다. 중대 오류 알림이 전달되며, 키보드/모바일 오버플로우 문제가 없고 실제 프린터 출력/재시도 결과가 기록된다.

### P3 — 파일럿 사용 데이터에 따른 UX·AI 확장

사용자가 실제로 쓰는 흐름에서 이탈·문의·오류를 관찰한 뒤 메뉴 디자인, 분할결제, 통합 데이터 대시보드, AI 매장 제안 순으로 개선한다. AI는 근거 데이터 기간·provider·신뢰도를 함께 표시하고 추천과 실행을 분리한다. 데이터량·추천 성공률·사업자 승인율·비용을 측정하기 전에는 자동 프로모션이나 매출 개선을 주장하지 않는다.

## 4. 실행 순서와 산출물

| 순서 | 게이트 | 산출물 | 선행 조건 |
|---:|---|---|---|
| 0 | RC 기준 고정 | 정제된 diff, 비밀정보 검사, 단일 RC SHA | 로컬 작업분·미추적 자료 분류 |
| 1 | 서비스 복구 | Render/Vercel health JSON, 로그인 안정성, `42P05` 원인/수정 기록 | 실제 배포 설정 읽기 권한 |
| 2 | DB 안전성 | 연결 참조 대조표, schema/journal diff, 격리 restore 보고서 | 비용 없는 로컬 복원 가능 대상 또는 승인된 격리 대상 |
| 3 | 핵심 E2E | 역할별 브라우저·API·DB 대사 결과 | staging DB, 테스트 계정, webhook 격리 |
| 4 | RC 품질 게이트 | 해당 SHA CI·빌드·보안 결과 | 단계 0~3 통과 |
| 5 | 제한 파일럿 판정 | 현금/이체 범위, 모니터링·롤백·지원 절차 | 운영 승인과 배포 SHA 일치 |
| 6 | 후속 통합 | 업체별 대사, sandbox 결제, 기기/UX 개선, AI 효용 지표 | 계약·키·원본 데이터·실기기 준비 |

한 단계의 미충족 항목은 다음 단계의 성공으로 상쇄하지 않는다. 특히 코드 테스트 성공은 DB 복원, 운영 배포, 실제 PG 승인 또는 실기기 검증을 대신하지 않는다.

## 5. 출시 완료 정의 (Definition of Done)

### 제한 파일럿 GO

- 단일 검토 RC SHA가 main/배포 후보와 일치하고 필수 CI·빌드가 통과한다.
- Vercel API proxy와 Render API health가 모두 JSON 정상 응답을 반환하며 로그인·세션 핵심 경로에 반복 5xx가 없다.
- 운영 DB 연결 대상과 migration 상태가 대사되고, 승인된 변경만 적용되며 격리 복원과 rollback 준비가 증명된다.
- 사업자·관리자·매니저·직원·주방·고객의 staging E2E가 통과하고 tenant 격리·중복 방지·현금/이체 원장 대사가 확인된다.
- Toss/카드 결제는 계약 전 비활성이고, 사용자가 볼 수 있는 안내와 서버 권한이 일치한다.
- 운영 장애 알림, 개인정보 로그 마스킹, 담당자 대응 및 롤백 절차가 검증된다.

### 일반 Production GO

제한 파일럿 기준에 더해, 실제 merchant 계약 후 테스트/운영 키 분리, 승인·부분/전체 취소·중복/역순 webhook·정산 대사, 갱신/실패/환불, 복구 가능한 백업/PITR, 업체 원장 대사, 부하 및 기기 검증을 해당 운영 범위에서 별도 승인·증거로 통과해야 한다.

## 6. 이번에 하지 않은 작업

운영 DB/API 재조회, 테스트 실행, migration 적용, Toss 결제·환불, webhook 발송, Git push/merge, Vercel/Render 배포는 수행하지 않았다. 이 문서는 실행계획이며 현재 상태를 Production Ready로 변경하지 않는다.
