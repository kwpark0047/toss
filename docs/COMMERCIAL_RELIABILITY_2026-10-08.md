# 상용 운영 신뢰성 개선

이번 변경은 운영 기반의 1차 구현이다. 업체별 연동·유료 인프라·운영 청구 활성화를 자동 완료하지 않는다. 기존 고객·주문·결제 테이블을 변경하지 않으며 신규 DB 마이그레이션이 없다.

## 요청 흐름

브라우저 → 제한 시간 적용(읽기 15초, 기본 쓰기 45초; 개별 설정 우선) → 안전한 읽기만 휴면 복구 → 401은 탭 내 공유 인증 갱신(12초) → 원래 요청 1회 복구. 만료/거절(401/403)만 인증정보를 제거하며 네트워크·5xx는 갱신 자격을 보존한다. 쓰기 응답 시간 초과가 거래 실패를 증명하지 않으므로 자동 재전송하지 않는다. 거래 상태 조회·멱등성 키로 확인한다.

인증 초기화와 API 인터셉터가 동일한 refreshSession을 사용한다. 현재 공유 범위는 브라우저 탭이며 여러 탭의 갱신 조정은 후속 작업이다.

## DB 및 상태 검사

별도 REPLICA_URL이 없거나 동일하면 주 DB 클라이언트를 재사용한다. 실 복제 DB를 지정한 경우에만 별도 풀을 만든다. 쿼리 로그에는 파라미터와 SQL 원문을 보관하지 않고 SHA-256 지문·소요시간·시각만 기록한다. 기존 외부 로그 저장소의 이미 기록된 자료는 별도 보존/삭제 정책을 적용해야 한다.

서버 listen 후 DB 연결을 비동기로 준비한다. `/api/health/live`는 프로세스 생존, `/api/health/ready` 및 기존 `/api/health`는 DB 준비 상태다. 준비 검사는 진행 중인 DB 쿼리 하나를 공유하며 응답은 최대 3초 기다린다. 호출자 제한 시간이 지나도 DB 쿼리를 강제로 취소하지는 않는다. 네이티브 드라이버의 connect_timeout·pool_timeout을 별도로 관리해야 한다. 클라이언트와 health 타이머를 정리하고 준비 결과를 1초 캐시한다.

무료 Render 휴면 자체나 DB 서비스 장애를 제거한 것은 아니다. 냉간/웜 지연을 따로 계측한 뒤 요금 변경 없이 해결 가능한 범위를 먼저 확인한다.

## 웹훅·청구 작업

웹훅은 기존 pending/attempt/next_retry_at 컬럼으로 발송 시도를 원자적으로 선점한다. 경쟁 작업자는 이미 선점된 시도를 보내지 않는다. 프로세스가 멈추면 2분 lease 이후 다음 시도가 가능하며, 최대 시도에 도달하면 failed로 종료한다. 늦은 응답은 동일 attempt 조건으로만 결과를 기록한다. 같은 프로세스의 겹치는 스케줄 tick을 막고 종료 시 타이머를 해제한다.

전달 보장은 at-least-once다. 수신자는 X-WeMarket-Delivery 기준으로 중복을 제거해야 한다. 전송 후 기록 전에 프로세스가 중단되는 상황에서 외부 전달을 정확히 한 번으로 보장하지 않는다. 실패 큐 화면·운영 수동 재처리·실업체 계약은 후속 작업이다.

API 프로세스에서는 WEBHOOK_RETRY_ENABLED=true일 때만 재시도 스케줄을 시작한다. 독립 작업자 진입점은 `node scripts/operations-worker.cjs`다. HTTP 서비스가 휴면해도 작업을 지속하려면 이 진입점을 별도 지속 실행 환경에서 운영한다. 작업자에서는 필요한 flag만 true, API에서는 해당 flag를 false로 설정해 역할을 분리한다. BILLING_SCHEDULER_ENABLED와 WEBHOOK_RETRY_ENABLED는 이번 작업에서 운영 활성화하지 않았다. 실제 구독 청구는 테스트 가맹점 갱신/실패/환급 확인 후 활성화한다.

## 배포 보증

CI의 smoke 대상은 현재 운영 wemarket-saas.vercel.app으로 통일했다. Render hook 및 Vercel 배포 인증정보가 없으면 운영 deploy job을 실패 처리한다. 이전처럼 건너뛰고 성공으로 보이지 않는다. readiness는 status ok / DB connected만 성공으로 인정한다. EXPECTED_COMMIT_SHA가 설정되면 백엔드 revision과 프런트엔드 app-commit 메타 값이 배포 커밋과 같아야 통과하며, 백엔드 배포 준비를 최대 120초 재확인한다. 운영 secrets가 미설정이면 먼저 등록해야 하며, PR 검사 통과가 운영 배포 완료를 뜻하지 않는다.

## 확장 단계

1. 실제 운영 배포·계측, 전용 키 회전·로그 보존 정비.
2. 지속 작업 환경과 청구/웹훅 실패 관측 및 운영 인수 테스트.
3. 업체 1곳의 공식 어댑터와 대사, 메뉴 매핑.
4. 통합 주문 사실 모델과 AI 지표 일치·보존 정책·자동 성과 평가.

이 단계는 실제 업체 규격·운영 계정·발급 키와 운영 데이터가 필요하다. API 키 등록 화면만으로 업체 연결이나 네이버 리뷰 원문 수집 완료를 표시하지 않는다.
