# QR 기반 데이터 통합과 매장성장 플랫폼

## 구현 범위

관리자 `/admin/stores/:storeId/integrations`에 데이터 통합 센터를 추가했다. 기존 QR·자체 주문과 POS, 테이블오더, 포인트기기, 카드단말기, 배달의민족, 온라인 주문의 정규화 기록을 같은 매장에서 조회한다. 외부 데이터는 CSV 또는 API 키로 실제 DB에 수집하며, 업체별 자동 수집 어댑터는 아직 연결하지 않았다.

원본 엑셀은 아래 규격의 UTF-8 CSV로 변환한다. 직접 XLSX 업로드는 이번 범위에 포함하지 않는다. 카드 승인, 주문 생성, 포인트 잔액 변경, 마케팅 발송은 수집으로 실행되지 않는다.

## 연결 절차와 API 계약

1. 관리자 통합 센터에서 채널·업체·연결 이름·수집 방식을 등록한다.
2. CSV 양식을 내려받고 업체 파일의 컬럼을 매핑한다. 최대 500행·1MB이다.
3. 미리보기로 검증한 뒤 수집한다. 오류가 있는 요청은 전체 거절한다.
4. API 방식은 개발자 센터에서 `integrations:write` 권한의 매장 API 키를 발급한다. 업체 시스템의 서버에서 `POST /api/integrations/events/{connectionId}`로 `X-API-Key`를 전송한다. 요청의 매장은 키에서 결정하며 `store_id`를 받지 않는다.

```json
{
  "events": [{
    "event_id": "pos-delivery-001",
    "record_id": "pos-order-001",
    "kind": "order",
    "version": 1,
    "occurred_at": "2026-10-07T12:00:00+09:00",
    "amount": 15000,
    "status": "paid",
    "currency": "KRW",
    "refund_amount": 0,
    "order_key": "store-order-001"
  }]
}
```

필수 CSV 컬럼은 `event_id,record_id,kind,version,occurred_at,amount,status`이다. 선택 컬럼은 `currency,refund_amount,order_key,native_order_id,customer_reference,marketing_consent,consent_at,consent_source`이다. 종류는 `order/payment/refund/loyalty`, 상태는 `pending/paid/cancelled/completed`이다. 금액은 원 단위 정수, 포인트는 POINT 단위이며 차감은 음수이다. 승인·환불 기록의 amount는 양수이다. 수정된 주문 스냅샷은 version을 증가시킨다.

응답은 accepted·duplicates·received를 반환한다. 재전송은 중복 제외하고 같은 이벤트 ID나 같은 거래 버전에 다른 내용이 오면 409를 반환한다. 잘못된 규격은 400, 다른 매장의 연결은 404, 중지된 연결은 409이다. API 키 권한과 JWT 관리자 권한은 각각 검사한다.

## 매출 정합성

- 매출은 paid/completed 주문의 `amount-refund_amount`로 계산한다. 결제·환불·포인트 이벤트를 다시 더하지 않는다. 이는 기간별 주문 기준 분석이며 실제 지급 정산서와 차이가 있을 수 있다.
- 기존 QR 주문을 외부 POS가 다시 보내면 `native_order_id`로 해당 매장의 주문을 지정한다. 외부 기록은 매출에 다시 포함하지 않는다. 기존 주문의 실제 취소·환불은 기존 주문 기능에서 처리한다.
- 외부 채널 간 같은 주문은 공통 order_key와 공통 version 규칙을 사용해야 한다. 매핑이 없으면 서로 다른 주문으로 취급되어 중복될 수 있다. 업체별 식별자 변환표를 반드시 확정한다.
- 같은 공통 주문 버전의 금액·환불·상태가 다르면 수집을 거절한다. 최신 버전을 먼저 선택하고 기간을 필터링하여 늦게 들어온 취소가 이전 매출을 되살리지 않도록 한다.
- 환불 이벤트만 전송해도 주문 순매출은 바뀌지 않는다. 주문의 refund_amount 누계를 반영한 새 버전을 함께 보낸다.
- 매장 단위 트랜잭션 잠금과 DB 고유 제약으로 동시 재전송을 제어한다. 최대 500행은 SQL 일괄 삽입한다.

## 업체별 연결 확보 항목

| 채널 | 최초 적용 | 자동 연동 전 확보 사항 |
| --- | --- | --- |
| POS·테이블오더 | 주문 CSV | 업체·모델·버전, API 계약, 주문/수정/취소 식별자, QR 주문 매핑 |
| 포인트기기 | loyalty CSV | 회원 ID 정책, 적립·차감·취소 API, 원장 대사 방법 |
| 카드단말기 | payment/refund CSV | VAN/PG 승인된 조회 API, 승인/취소 식별자, 주문 연결키 |
| 배달의민족 | 허용된 내보내기 자료 | 판매자 계약·공식 접근 권한, 주문/취소/수수료 규격 |
| 온라인 주문 | CSV·인증 API 수집 | 웹훅 재전송 규칙, 주문키·버전 매핑, 인증정보 보관 |

화면의 API 수집 연결 등록은 업체 API 자동 연결 완료를 의미하지 않는다. 기존 계정·비밀번호를 스크래핑하거나 비공식 우회 API를 사용하지 않는다. API 키는 서버에서 보관하고 유출 시 폐기·재발급한다.

## 고객·AI·CRM·마케팅 추가기능 기획

| 단계 | 추가 기능 | 완료 기준 |
| --- | --- | --- |
| 1. 데이터 기반 | 업체별 어댑터, 취소·환불 대사, 누락/충돌 알림 | 실제 업체 자료와 주문 건수·순매출 일치, 실패 재시도와 감사 기록 |
| 2. 고객 연결 | QR 동의 화면, 검증된 회원 연결, 동의/철회 이력 | 본인 확인 후만 고객 병합, 철회 즉시 반영, 보존/삭제 정책 적용 |
| 3. CRM 실행 | 신규·단골·이탈 위험 세그먼트, 방문 후 혜택, 승인형 캠페인 | 점주 승인, 발송 직전 동의·수신 거부 검사, 중복 발송 차단 |
| 4. AI 성장 | 메뉴·시간대·채널 분석과 개선 제안 | 근거 기간·표본·비용 표시, 데이터 부족 표시, 실행 전 승인 |
| 5. 효과 측정 | 캠페인/쿠폰/QR 주문 연결, 대조군, 재방문·순이익 | 환불·할인·채널 비용 반영, 매출 증가와 자연 재방문 구분 |

외부 customer_reference는 매장·연결별 해시로 저장한다. 원문 연락처를 수집하지 않으며 기존 CRM 고객과 자동 병합하지 않는다. 해시는 법적 익명화를 보장하지 않는 가명 데이터이므로 접근·보존·삭제 정책이 필요하다. 마케팅 동의 기록에는 일시·근거 식별자가 필요하지만 이 기록만으로 문자 발송을 허용하지 않는다. 배달의 가려진 연락처를 고객 연결키로 사용하지 않는다.

기존 고객 관리·캠페인·AI 추천 분석 화면으로 연결하는 기획 탭을 추가했다. 신규 자동 고객 병합, AI 추천 실행, 실제 메시지 발송·성과 귀속은 위 단계별 후속 구현 대상이다. 구독 요금은 변경하지 않는다.

## DB 적용과 검증

신규 마이그레이션 `20261007010000_store_data_integrations`는 integration_connections·integration_events 두 테이블과 관련 제약·인덱스를 추가한다. 기존 주문·고객 데이터를 수정하지 않는다. 운영 적용 전 별도 검증 DB에서 마이그레이션 및 동시성 테스트를 통과시킨다. 기존 미적용 마이그레이션 목록을 먼저 확인하고 무조건 전체 migrate deploy를 실행하지 않는다.

실제 PostgreSQL 검증은 `scripts/test-store-integrations-postgres.cjs`를 실행한다. localhost의 wemarket_test DB만 허용하고 별도 임시 스키마에서 실제 SQL을 검증한 뒤 정리한다. CI의 PostgreSQL 서비스에서도 실행한다. SaaS 계약 테스트는 `npm run test:saas`, 프런트엔드 검증은 frontend의 `npm run build`이다.
